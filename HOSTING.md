# Размещение на GitHub Pages

Приложение полностью статическое: GitHub Pages не запускает Node.js, поэтому здесь нет API-роутов и Prisma. Всё, что нужно для работы, выполняется в браузере:

- метки рисуются на canvas;
- **общая история** хранится в Supabase (PostgreSQL) и видна всем устройствам;
- **IndexedDB** используется как локальный кэш и офлайн-копия;
- без ключей Supabase приложение работает только локально.

## Быстрый старт

1. Создайте репозиторий на GitHub и запушьте в него проект:
   ```bash
   git add -A
   git commit -m "Генератор меток"
   git remote add origin https://github.com/USER/REPO.git
   git branch -M main
   git push -u origin main
   ```
2. Откройте **Settings → Pages** и в разделе **Build and deployment** выберите источник **GitHub Actions**.
3. Workflow `.github/workflows/deploy.yml` сам соберёт сайт и опубликует его. Ссылка появится во вкладке **Actions → Deploy to GitHub Pages** и в **Settings → Pages**.

Для project pages адрес будет таким:

```
https://USER.github.io/REPO/
```

Если репозиторий называется `USER.github.io`, сайт откроется в корне:

```
https://USER.github.io/
```

Базовый путь (`/REPO` или пустой) workflow передаёт в `NEXT_PUBLIC_BASE_PATH`. Вручную его прописывать не нужно.

## Что происходит при деплое

1. `actions/configure-pages` вычисляет базовый путь.
2. `npm ci` ставит зависимости по `package-lock.json`.
3. `npm run build` собирает статический сайт в папку `out/`.
4. `actions/upload-pages-artifact` и `actions/deploy-pages` публикуют `out/`.

В `public/.nojekyll` лежит пустой файл — он не даёт GitHub Pages трогать папку `_next`.

## Локальный запуск

```bash
npm install
npm run dev
```

Проверка production-сборки:

```bash
npm run build
npm run preview
```

`npm run preview` запускает статический сервер на `http://localhost:3000`.

Если нужен локальный запуск с базовым путём:

```bash
# PowerShell
$env:NEXT_PUBLIC_BASE_PATH="/my-repo"; npm run build
```

## Где хранятся метки

Есть два уровня хранения:

**Общая БД — Supabase (если заданы ключи).** Это основная история: её видят все пользователи сайта с любых устройств. В таблице `public.markers` лежат:

- `id` — ID метки, выводится из названия;
- `name` — название;
- `cells` — сам узор (тёмные ячейки);
- `created_at`, `updated_at` — даты.

Приложение подтягивает изменения каждые 20 секунд и при возврате на вкладку. Добавление, удаление и очистка сразу уходят в общую БД.

**Локальный кэш — IndexedDB.** Нужен, чтобы список открывался мгновенно и работал без сети:

- база: `qr-marker-studio`;
- хранилище: `markers`;
- ключ: ID метки.

Если IndexedDB недоступна (приватный режим, старый браузер), приложение переходит на `localStorage`, а в крайнем случае держит историю в памяти на время сессии. Старая история из `localStorage` автоматически переносится в IndexedDB.

При первом включении Supabase локальная история один раз загружается в общую БД, если та пуста. Дальше общая БД считается главной, а локальная — кэшем. Если сеть пропала, приложение показывает кэш и помечает статус «БД недоступна».

**Важно:** без Supabase история привязана к браузеру и домену. Очистка данных сайта удалит локальную копию.

## Общая БД на Supabase

1. Создайте проект на [supabase.com](https://supabase.com) (бесплатного тарифа достаточно).
2. Откройте **SQL Editor → New query**, вставьте содержимое `scripts/supabase-schema.sql` и нажмите **Run**.
   - SQL создаёт таблицу `markers` с полной записью метки.
   - Старая таблица с одними названиями удаляется. Если в ней уже были данные — сохраните их заранее.
3. В GitHub откройте **Settings → Secrets and variables → Actions** и добавьте секреты:
   - `NEXT_PUBLIC_SUPABASE_URL` — Project URL;
   - `NEXT_PUBLIC_SUPABASE_ANON_KEY` — anon public key.
4. Перезапустите workflow (Actions → Deploy to GitHub Pages → Re-run all jobs) или сделайте новый push.

После сборки в шапке истории появится чип **«Общая БД»**, а в подвале — `БД: Supabase`. Если чип показывает **«Локально»**, ключи не попали в сборку.

Секреты попадают в клиентский бандл как публичные ключи Supabase (anon-ключ публичен по дизайну, доступ ограничивается RLS-политиками из SQL-файла). В текущей схеме чтение и запись разрешены всем с anon-ключом: любой, у кого есть ссылка на сайт, может менять общий список. Если это критично, нужен вход через Supabase Auth — тогда политики заменяются на проверку `auth.uid()`.

## Форматы файлов

| Кнопка | Что внутри | Зачем |
| --- | --- | --- |
| **Скачать JPG** | 2048×2048, JPEG, RGB, без названия и без прозрачности | Загрузка в Vuforia |
| **PDF** | A4, метка с названием, точный размер 10/13/16 см | Печать |
| **PDF всех** | A4-сетка со всеми метками из истории | Печать набора |
| **JPG** в истории | тот же Vuforia-формат без названия | Повторное скачивание |

Vuforia жалуется на «неподдерживаемый тип цвета» у PNG с альфа-каналом или нестандартным цветовым профилем. Поэтому скачивание теперь сразу отдаёт JPEG: canvas залит непрозрачным белым, а JPEG всегда кодируется как 8-битный RGB (JFIF, без альфы). Конвертировать вручную больше не нужно.

## Свой домен

1. **Settings → Pages → Custom domain** — укажите домен.
2. В DNS настройте CNAME на `USER.github.io` (для поддомена) или A-записи GitHub Pages (для корневого домена).
3. Для деплоя через Actions положите файл `CNAME` с доменом в `public/` — он попадёт в `out/` и сохранит домен между деплоями.

После подключения домена базовый путь остаётся пустым, workflow определит это автоматически.

## Частые проблемы

**Открывается 404 или белая страница, в консоли 404 на `/_next/...`.**
Проверьте, что сборка шла через workflow, а не вручную без `NEXT_PUBLIC_BASE_PATH`. Для project pages путь должен быть `/REPO`.

**После обновления осталась старая версия.**
Обновите страницу с очисткой кеша (Ctrl+F5). Service worker обновляется сам, но вкладку со старым HTML иногда нужно перезагрузить дважды.

**Workflow падает на `npm ci`.**
Убедитесь, что `package-lock.json` закоммичен. Файл `.npmrc` уже включает `legacy-peer-deps=true` — это нужно из-за соседства React 19 и старых UI-пакетов.

**Не работает Supabase.**
Проверьте, что оба секрета заданы и workflow перезапущен. В браузере откройте DevTools → Network и посмотрите запросы к `/rest/v1/markers`: если их нет, ключи не попали в сборку; если есть `401/403`, проверьте RLS-политики и SQL-схему.

**Нужна серверная БД, но Supabase не подходит.**
GitHub Pages не умеет запускать серверный код. Общее хранилище в любом случае будет внешним: Supabase, Firebase, Neon + собственный API на Render/Railway или другой хостинг с Node.js.
